# VisualXtsi

A C++ and Unreal Engine productivity extension for Visual Studio 2022 and later, built for large,
multi-platform (including console) codebases, with first-class support for Unreal Engine C++
(UE 4.27 and all UE5 versions).

What it focuses on:

- **Unreal-aware parsing**: Unreal's macros and reflection markup (UCLASS, UPROPERTY,
  GENERATED_BODY, ...) and the code UnrealHeaderTool generates are understood rather than guessed,
  including BlueprintNativeEvent and RPC functions implemented by Name_Implementation.
- **Project settings from Unreal Build Tool**: compile arguments come from the project files UBT
  generates (UE 4.27 and UE5 layouts, forced includes included) or a compile_commands.json, with no
  manual setup.
- **Background parsing with per-module PCHs**: files are parsed off the UI thread, and each
  module's shared headers are precompiled once and reused.
- **Navigation and indexing at engine scale**: file and symbol indexes that keep up with whole
  projects and, if wanted, the engine source.

## Architecture

- **engine/**: a native C++ DLL that holds all of the real logic (parsing, classification,
  and later indexing and navigation). It exposes a flat C ABI (`vx.h`). It doesn't use C++/CLI.
- **vsix/**: a thin C# VSIX shell. It exists only because Visual Studio's editor extension
  points (MEF classifiers, QuickInfo, etc.) are managed-only. It forwards work to the engine
  through P/Invoke.

Text offsets crossing the ABI are in UTF-16 code units, matching the VS editor buffer.

## Building

Requirements: Visual Studio 2022 with the "Desktop development with C++" and
"Visual Studio extension development" workloads, CMake 3.20+, and an LLVM 19 install
(for libclang; the official `clang+llvm-19.1.5-x86_64-pc-windows-msvc` archive or the
`LLVM-19.1.5-win64.exe` installer). Point `VX_LLVM_ROOT` at it (CMake cache variable or
environment variable; default `C:/Program Files/LLVM`). Without it the engine still builds,
with lexical classification only.

```
cmake -S engine -B build/engine -G "Visual Studio 17 2022" -A x64 -DVX_LLVM_ROOT=<llvm root>
cmake --build build/engine --config Release
ctest --test-dir build/engine -C Release
msbuild vsix/VisualXtsi.Vsix/VisualXtsi.Vsix.csproj -restore -p:Configuration=Release -p:VxLlvmRoot=<llvm root>
```

## Compile arguments

The engine finds arguments for a file by itself (`vx_discover_args`): first a
`compile_commands.json` in a parent folder that lists the file, then the Unreal Build Tool
project files of the enclosing project (`Intermediate/ProjectFiles/*.vcxproj`, generated by
"Generate Visual Studio project files"; UE 4.27 and UE5 layouts). Headers use the arguments
of the nearest source file of their module. Files are parsed in the background when opened
and reparsed shortly after edits; progress is logged to
`%LOCALAPPDATA%\VisualXtsi\VisualXtsi.log`. Function bodies in included headers are skipped
(the open file keeps its own), which makes first parses about a third faster and reparses
about four times faster on Unreal code; set `VX_FULL_PREAMBLE=1` to compare against full parsing.

After the first file of an Unreal module is parsed, a shared precompiled header for the module
is built in the background: the engine and plugin headers that at least a fifth of the module's
source files reach (directly or through the project's own headers), leaving out any that do not
compile on their own. Later files of the module start from it (on Lyra, about 1.5 s instead of
about 4 s). PCHs live in `%LOCALAPPDATA%\VisualXtsi\pch`, are rebuilt when the module's
arguments or any header in them changes, and the least recently used ones are evicted beyond
`VX_PCH_CACHE_MB` (default 4096).

## Coloring

Two classifiers feed the editor. A lexical one (instant, no parsing) colors preprocessor
directives and macro-like names. A semantic one colors identifiers by what they name (locals,
parameters, member fields, globals and statics, types, enum constants, namespaces, functions,
methods, static and virtual methods), using the last background parse; edits only recolor the
spans whose classification changed. Keys inside Unreal reflection markup (UCLASS(...), UPROPERTY(EditAnywhere, meta=(ClampMin=...)), UFUNCTION(...) and the like) get their own "Unreal reflection specifier" color, lexically, since the macros expand to nothing; hovering a well-known specifier shows a one-line description. Every category has its own entry under Tools > Options >
Environment > Fonts and Colors (names start with "VisualXtsi"); defaults suit the dark theme.

## Navigation

| Command (Keyboard options name) | Default key | What it does |
| --- | --- | --- |
| `VisualXtsi.ToggleHeaderSource` | Alt+O (editor) | Header ↔ source: same folder, Unreal Public/Classes ↔ Private, the module, include paths |
| `VisualXtsi.OpenFileInSolution` | Shift+Alt+O (editor) | Fuzzy file search over the solution folder and Unreal project(s); `name:123` opens at a line |
| `VisualXtsi.FindSymbolInSolution` | Shift+Alt+S | Fuzzy search over a persisted index of the project's declarations; `Scope::name` narrows |
| `VisualXtsi.GoToDefinition` | Alt+G (editor) | Definition of the symbol at the caret (libclang, then the symbol index); on a definition, its declaration. C#: see below |

Alt+O, Shift+Alt+O and Alt+G are bound in the Text Editor scope: Visual Studio binds the last two
globally (File.OpenWebSite, Edit.BriefBrowse), other extensions often take Alt+O and Alt+G, and in an
editor a Text Editor binding outranks global ones. If another tool still takes a key, rebind the
command under Tools > Options > Environment > Keyboard (Extensions > VisualXtsi > Help >
Keyboard Shortcuts opens it filtered to VisualXtsi's commands).

The commands work in C# editors too, so the keys stay the same when moving between the C++ and
C# projects of a solution. Alt+O in C# goes between a form and its Designer.cs and from XAML
code-behind to its .xaml. From an Unreal module's Name.Build.cs, Alt+O goes to the source that
implements the module, the .cpp whose IMPLEMENT_MODULE, IMPLEMENT_GAME_MODULE or
IMPLEMENT_PRIMARY_GAME_MODULE names it (wherever it is and whatever it is called; only without such
a macro is Name.cpp or NameModule.cpp assumed). If that source has a header, Alt+O goes to the
header and from there toggles header and source as usual; a header-less one goes back to the
Build.cs. Alt+G on a module name in a
Build.cs or Target.cs string ("Core" in PublicDependencyModuleNames) opens that module's
Build.cs, from the project or from the engine the project uses (found like UnrealBuildTool finds
it, an Engine folder above the project or the .uproject's EngineAssociation; its Build.cs files
are listed once, in about a second). Elsewhere in C#, Alt+G is Visual Studio's Go to Definition;
in C# files that belong to no C# project, such as Build.cs and Target.cs, the C# symbol index is
tried first, since Visual Studio knows little about them.

Unreal's split UFUNCTIONs are understood: a BlueprintNativeEvent or Server/Client/NetMulticast RPC
is implemented by Name_Implementation (and, with WithValidation, Name_Validate). Go to Definition
on the declaration or a call goes there (a list when there are both), and from those back to the
UFUNCTION declaration; hovering the declaration shows "Implemented by ..." with a link; Find
Symbol labels the declaration and its implementations. The symbol index records the split from the
UFUNCTION specifiers lexically (cache format 2). The engine can be indexed
as well, with its plugins and platform extensions (Platforms\<Platform>\..., also under
Restricted): Options > VisualXtsi > Navigation, off by default, about 1 GB or more.

C# files are indexed too (a C# tool project in the solution, Unreal's *.Build.cs and *.Target.cs,
the engine's own C# programs when the engine is indexed), by a separate lexical scanner that knows
C#: verbatim, interpolated and raw strings, attributes, file-scoped namespaces, records (whose
positional parameters are properties), properties, events, interfaces, delegates, operators and
expression-bodied members. Their scopes read "Namespace.Class", and Find Symbol takes
"Scope.name" as well as "Scope::name". Find Symbol has a Language column and a Language box (All
languages, C/C++, C#); lookups from C++ (Go to Definition's fallback, the UFUNCTION tooltips) only
consider C/C++ symbols.

## Menus and dialogs

Extensions > VisualXtsi groups the commands by task: Open File in Solution and Toggle
Header/Source | Find Symbol in Solution | Go to Definition | Tools (Rebuild Symbol Index,
Clear PCH Cache, Open Log File) and Help (About, Keyboard Shortcuts) | Enable/Disable VisualXtsi
and Options. Every item has an icon, an access key and its shortcut; editor commands are disabled
(not hidden) where they cannot run. The navigation commands are also in the Edit menu and the
code editor's context menu. Enable/Disable (checked while on) stops coloring, tooltips, parsing,
indexing of newly opened projects and the navigation commands without unloading anything.

The search dialogs (Open File, Find Symbol, the Go to Definition picker) are keyboard-first:
focus starts in the search box, Up/Down/PageUp/PageDown move through the results from there,
Enter opens and closes, Ctrl+Enter opens and keeps the dialog open, Esc closes, and labels have
access keys. Results show an icon, the matched characters in bold, and sortable columns (header
click or the "Sort by" box); rows expose name, kind and location to screen readers, and the
result count is announced as a live region. The dialogs follow the Visual Studio theme
(including high contrast), the environment font and the Windows text size, and remember their
size, position, column widths and sorting.

## Options

Extensions > VisualXtsi > Options... opens the VisualXtsi Options window, a floating tool window
that does not block Visual Studio (switch editor tabs and scroll while it is open, on any monitor;
color and theme changes show in the editors right away with "Live preview in the editor", and
Cancel or Esc goes back to the applied colors). It has every setting
in one place: Coloring and Attributes, Tooltips, Navigation, Parsing and Performance, Unreal
Engine, Keyboard and System Info, with a description of the focused or hovered setting at the
bottom. The coloring page has a master switch, where coloring applies (editor, QuickInfo, Find
Symbol results), and per category an on/off switch, foreground and background colors
(theme-aware named colors, a hex value or the Windows color dialog), bold, italic and a reset
to the theme default, plus a live preview. Colors and bold are the Fonts and Colors > Text
Editor entries themselves (read and written through IVsFontAndColorStorage), so both always
agree; italic is a VisualXtsi setting because Fonts and Colors has none. The Keyboard page
changes shortcuts through Visual Studio's binding API and shows which commands already use a
key. OK and Apply apply; Cancel restores everything as it was when the dialog opened, including
changes already applied. Compile arguments can be limited to compile_commands.json or to the
Unreal project files (engine `vx_config.args_source`).

Coloring themes are named sets of colors and font attributes for all categories, each with a dark
and a light variant; the variant follows Visual Studio's light or dark theme (and switches with it)
unless set to always dark or always light. The built-in themes are Xtsi Default, Xtsi Muted, Xtsi
Vivid, High Contrast (at least 4.5:1 on the editor background) and palettes adapted from Solarized,
Nord, gruvbox, Dracula and One (see THIRD_PARTY_NOTICES.md). Your own themes (New, Save, Save As,
Rename, Delete, Import, Export) are JSON files in `%LOCALAPPDATA%\VisualXtsi\themes\*.xtsitheme`, easy
to share with a team. C# adds categories C++ has no use for (properties, events, interfaces,
delegates, type parameters and attributes); the other categories color both languages, so one
theme covers a mixed solution. Theme files written before these categories existed (schema 1)
still load, the missing categories taken from fields and types.

Tools > Options > VisualXtsi > General is the compact version (with a button that opens the
dialog). It holds what Fonts and Colors cannot: switching each
coloring category and the macro tooltip on or off, skipping function bodies in included headers,
the shared PCH and its cache size limit, and a button that clears the PCH cache. Settings are
stored in the Visual Studio user settings store (collection "VisualXtsi") and are also
available to automation as `DTE.Properties("VisualXtsi", "General")`. The environment variables
`VX_FULL_PREAMBLE`, `VX_PCH_CACHE_MB` and `VX_PCH_DIR` override the parsing settings.

## Packaging

A release package is one command; it builds the engine, runs its tests, builds the VSIX and
checks its contents, writing `dist\VisualXtsi-<version>.vsix` (version from the manifest):

```
powershell -ExecutionPolicy Bypass -File scripts\package.ps1 -LlvmRoot <llvm root>
```

The build copies `libclang.dll` and clang's builtin headers (`clang-resource/include`)
next to `vxengine.dll`, and the VSIX packages them. `vxcli` (built with the engine) parses a
file and prints macro information: `vxcli <file> [@args.rsp] [line:col ...]`.
